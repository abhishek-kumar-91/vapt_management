# Integration plan

This plan builds [database-architecture.md](database-architecture.md) v2 in 11 phases. **The app works at the end of every phase.** Each phase is one branch and one PR, or a few PRs where a phase is split. A phase starts only when the previous phase's exit checks pass.

## Rules for every phase

1. **Add the new path, switch over, then delete the old one.** Nothing is removed until its replacement passes its checks.
2. **The gate before merging:** `pnpm typecheck && pnpm lint && pnpm test && pnpm build` all pass, plus the phase's manual checks in a browser.
3. **Databases:** development and tests run on a local Postgres (`vapt_dev`, `vapt_test`); the Neon database is only touched on purpose, and `pnpm db:reset` refuses non-local URLs. Migrations are generated by `drizzle-kit`, committed, and applied with `pnpm db:migrate`. After phase 1, migrations only ever move forward; a mistake is fixed with a new migration.
4. **Additive database changes first.** A new column is nullable or has a default, backfilled, then tightened in a later migration. Renames happen as add, copy, then drop.
5. **Every server write** follows one pattern: `ctx` → permission check → `withOrg` transaction → change → audit row → return.
6. **Doc in step with code.** If a phase changes the design, `database-architecture.md` is updated in the same PR.

## Sequence

```
P0 Groundwork ─► P1 Schema v2 + auth on memberships ─► P2 /o/[org] routing ─► P3 Email outbox + links
      ─► P4 Sign-up & onboarding ─► P5 Admin: approvals & companies ─► P6 Products page, team & access
      ─► P7 Domain data to DB ─► P8 Testing requests ─► P9 Hardening & scale ─► P10 Email go-live (on hold)
```

Why this order:
- Identity and tenancy (P1, P2) come first because every later feature takes `ctx`.
- Email links (P3) come before sign-up because sign-up depends on them.
- Approvals (P5) complete the company lifecycle before any company data moves.
- Product access (P6) comes before the domain move (P7). Otherwise testers and developers would see nothing once scoping is enforced.
- Row-level security goes live (P9) only after every query runs through `withOrg`.

## P0 · Groundwork
**Goal:** a safe base and a test harness. No change in behaviour.

- Delete `app/audit-preview/` (it renders the console without a session).
- Fix the stale argon2id comment in `db/schema/auth.ts`.
- Add **Vitest** with the `@/*` path alias, `server-only` mapped to an empty module, and `pnpm test`. Move `lib/auth/roles.check.mjs` into it.
- Add a test-database setup. `TEST_DATABASE_URL` points at a local Postgres. It is wiped and re-migrated once per `pnpm test` run, and tests use unique emails and slugs so they never collide.
- Add `pnpm db:reset` (drop the schema, then migrate), allowed only when the URL isn't the production database.
- Local databases `vapt_dev` and `vapt_test`. Put the variables in `.env.example`: `DATABASE_URL`, `TEST_DATABASE_URL`, `AUTH_SECRET`, `EMAIL_TRANSPORT=log`, `APP_URL`, `CRON_SECRET`.

**Exit checks:** `pnpm test` runs the roles tests. Sign-in and the Users page behave exactly as before.

## P1 · Schema v2 + auth on memberships
**Goal:** the new tables exist and today's features run on them.

**Database** (squashing is safe because main has no data):
- Replace `0000_init` and `0001_guards` with `0000_v2.sql`, the whole v2 schema from the architecture doc, all tables included even where unused.
- Write `0001_guards.sql`: append-only audit log, `users_protect_platform_role`, `memberships_keep_an_owner`, RLS policies on every company table (not active yet), and the `app_user` role with its grants.

**Code:**
- `lib/auth/roles.ts`: an org-role matrix plus product access (`view`/`edit`), and Super Admin passes every check. Update the tests to the new table.
- `lib/auth/session.ts`: the session returns the user and `platform_role` only; memberships load per company.
- `server/context.ts`: `getContext(orgSlug)` and `withOrg(ctx, fn)`.
- Move `lib/auth/users.ts` to `server/members.ts`, working on `memberships`: invite (`org_invite` token with role), edit role, suspend, remove, reset link.
- `scripts/create-user.mjs` creates Super Admins (several allowed). New `scripts/seed.mjs` creates one active demo company, its Owner and a few members from `data.json`; **it creates no domain rows yet**.
- **Temporary bridge:** `/dashboard` resolves the user's first active membership, or the demo company for a Super Admin, and builds `ctx` from it. The domain pages still read localStorage.

**Exit checks:**
- Tests: the roles matrix; `memberships_keep_an_owner` refuses removing the last Owner; a member of company A gets nothing from company B through `server/members.ts`.
- Browser: sign-in, Team list, invite → link → set password → signed in as that role, suspend and reactivate, reset link. All v1 "Verified" checks still pass.

**Rollback:** revert the PR and point `DATABASE_URL` back at the untouched v1 branch.

**As built:**
- Invites create the membership (`invited`) at invite time. The token only carries `org_id`. A new person sets their password at `/set-password/<token>`, which also activates the membership and marks the email verified. Invites to an existing account link to `/invite/<token>`, which phase 3 builds.
- Name and email belong to the person. The Team page can correct them only while the invite is pending and it's their only company.
- Suspending or removing a member signs them out only if they have no other active company. A password reset link can't be made for someone who also belongs to another company.
- `pnpm db:seed` creates `admin@pentestscout.com` (Super Admin), Demo Company (Owner, Manager, Tester, Developer), Acme Corp, and Northwind Traders (waiting for review). The password for all of them is `scout-demo-2026!`.

## P2 · Company routing
**Goal:** the console lives at `/o/[org]`.

- Move `app/dashboard/*` to `app/o/[org]/*`. The layout calls `getContext` and returns 404 without membership. A company that isn't `active` redirects to `/onboarding`.
- `/dashboard/**` redirects to `/o/<last company>/**`. The last company is kept in a cookie, `/admin` is the fallback for Super Admins, and `/onboarding` for users without a company.
- Update every `href` in the sidebar, search, notifications and product links to include the company slug. Add a helper, `orgHref(path)`.
- **Key localStorage by company** (`vapt-dashboard-data-v1:<orgId>`) so two companies never mix data before P7.
- Sidebar header becomes a company switcher, shown only with more than one membership. Super Admins see the "Acting in <company>" banner.
- `proxy.ts` gate covers `/o`, `/admin` and `/onboarding`.

**Exit checks:**
- Old bookmarks (`/dashboard/findings`) land on the right page.
- A member of company A visiting `/o/b` gets 404.
- A Super Admin can open any company and sees the banner.
- Every link in the console stays inside the current company.

## P3 · Email outbox and links
**Goal:** every email-based flow works end to end without a mail provider.

- `lib/email/`: `sendEmail()`, the `log` and `outbox` transports, and plain-text plus HTML templates.
- `/verify/[token]` sets `email_verified_at`, and handles an expired or used link with a "Send a new link" action.
- `/invite/[token]`:
  - **New person:** name and password, which creates the user and an active membership, then signs them in.
  - **Existing user who is signed in:** an "Accept" button.
  - **Existing user who is signed out:** sign in, then accept.
- `/forgot-password` sends a `password_reset` email. The response is the same whether or not the account exists.
- Owner invites and reset links also go through `sendEmail`. The copy-link dialog stays.
- Development: the link appears on the "Check your email" screen when `EMAIL_TRANSPORT=log`.

**Exit checks:**
- Tests: tokens are single-use, expire, and are cancelled by a newer token; the outbox link is blanked once its token is used.
- Browser: every link type works from a copied outbox link, including expired and used links.

## P4 · Sign-up and onboarding
**Goal:** a stranger can sign up and submit a company for review.

- `/signup` (name, work email, password) → user, `verify_email` email → "Check your email" page. Throttled per IP and per email from `audit_logs`, plus a hidden honeypot field.
- `/onboarding/company`: name, slug (checked live; reserved words refused), industry, size, website → `organizations(status: draft)` and an Owner membership.
- `/onboarding/products`: add at least one product (name, tier, domain, technology, data sensitivity); test areas are filled from the tier template. **These are real `products` and `test_areas` rows.**
- `/onboarding/review`: a summary, then Submit → `pending_review` and an `org_submitted` email to Super Admins. Submitting needs a verified email.
- Status pages: "Under review" (editable), "Rejected" (reason, edit and resubmit), "Changes requested".
- Signing in sends people to the right place: no company → `/onboarding/company`; draft or rejected → onboarding; pending → under review; active → `/o/<org>`.

**Exit checks:** an end-to-end browser run from sign-up to verify to company to products to submit. Then sign out and back in, and you land on "Under review". A duplicate slug is refused, an unverified email can't submit, and the sign-up throttle works.

## P5 · Admin: approvals and companies
**Goal:** the full company lifecycle works.

- An admin layout reusing `ConsoleShell` with the admin navigation; `/admin` is gated on `platform_role`.
- **Approvals:** the pending queue, oldest first. The detail page shows the company, its products and the Owner. Actions: approve, reject (reason required) or request changes (note required). Each one writes an audit row and an email.
- **Companies:** a paginated list (search, filter by status) and a detail page with members, products, status history, suspend/reactivate and "Open console".
- **Sign-ups:** the derived funnel, with "Resend verify link".
- **Outbox:** a pending list with "Copy link".
- **Users:** global search, the companies each person belongs to, disable a user, and a reset link.
- **Audit log:** filters by company, actor, action and date.
- Counts on Approvals come from simple `count(*)` queries for now; `org_stats` arrives in P9.

**Exit checks:** sign-up → submit → Super Admin approves → Owner signs in and reaches `/o/<org>`. Rejecting and resubmitting works, and so does requesting changes. Suspending a company locks its members out while the Super Admin can still enter.

## P6 · Products page, team and product access
**Goal:** Owners manage products and who can work on them. The console stays on localStorage for findings and the other domain data.

- `/o/[org]/products`: list, "Add product" (Owner), archive.
  - The sidebar shows pinned and recent products plus "All products".
  - **Product data now comes from the DB.** For the remaining localStorage domain data, the store is seeded with the company's DB products on first load (bridge until P7).
- `/o/[org]/team` replaces Users. It covers members, roles, invites, and a **product access** column (multi-select products, `view`/`edit` each). The same picker appears in the invite form.
- `useCan(permission, productId)` covers the whole console: buttons and forms hide according to role and product access.
- Settings → Organization: name, prefix (locked after the first finding), retest email, Jira base URL, saved to `organizations`. The localStorage settings are removed.

**Exit checks:**
- Owner adds a product and invites a tester with edit on product X.
- The tester sees only X and can edit it.
- A developer with view sees X read-only.
- Changing access applies on the next request.

## P7 · Domain data to the DB
**Goal:** localStorage and `data.json` are gone, and everything runs through `server/*`. This is the largest phase, split into PRs that each leave the app working.

**Approach:** keep the `useDashboard()` interface so the ~18 consuming components barely change.
- `server/dashboard.ts` `loadDashboard(ctx)` returns today's `DashboardData` shape, scoped to the company and the user's product access.
- The `/o/[org]` layout passes it to `DashboardProvider`.
- Each store action becomes a server action call followed by `router.refresh()`.
- Each step switches one group of actions from local writes to server writes.

| Step | Moves | Server rules that leave the browser |
|---|---|---|
| 7a | **Read path:** `loadDashboard` reads products, areas and cycles from the DB. Findings, events and reports still come from localStorage, merged. | – |
| 7b | Test areas, cycles, product register | Tested needs a method and result; Blocked needs a reason; status changes need a reason; close-out criteria |
| 7c | Findings: create, edit, status, retest request | Key from `next_finding_no`; due and retest dates computed on the server; `canTransition`; refusals audited as denied; late-finding area reopen and escalation events in one transaction |
| 7d | Activity events (written by 7b and 7c) and the manual activity entry | – |
| 7e | Reports: save, list, close-out by `product_id` | – |
| 7f | Coverage snapshots and the trend chart | Snapshot on change |
| 7g | **Cleanup:** remove the localStorage persistence, the `data.json` import, "Reset local data" and export-local. Export becomes a server download with an audit row. | – |

`scripts/seed.mjs` gains a `--domain` option that loads `data.json` into the demo company, for development and tests.

**Exit checks:**
- Two browsers as two users in the same company see each other's changes after a refresh.
- A tester can't change a product they only have view on, even when calling the server action directly (test).
- Every write leaves an audit row and the right activity event.
- No `localStorage` use remains except UI preferences and notification read state.

## P8 · Testing requests
**Goal:** a company can ask Pentest Scout to test a product.

- Owner: "Request testing" on a product, `/o/[org]/testing` list and detail, cancel before `in_progress`.
- Admin: the Testing requests queue. Actions: accept, decline (note required), schedule (dates, assignee), start and complete.
- Findings raised by a Super Admin while a request is `in_progress` get `testing_request_id` and the "Raised by Pentest Scout" label. A close-out report links to the request.
- Emails for each status change.

**Exit checks:** request → accept → schedule → start → Super Admin raises a finding in the company → Owner sees it labelled → complete.

---

## P9 · Hardening and scale
**Goal:** production-ready for 1,000+ companies.

- **Turn on row-level security:** the app connects as `app_user` (not the owner). Before switching, run the whole test suite plus a new **isolation suite**: for every `server/*` read, a member of company A gets zero rows from B.
- `org_stats` is updated in the transactions that change findings and products, and rebuilt nightly. Admin Overview and the Companies list read from it, with keyset pagination.
- Cron (`/api/cron/*` with `CRON_SECRET`): abandoned sign-ups, SLA reminders, daily coverage snapshots, `org_stats` rebuild, outbox purge.
- `audit_logs` gets an `org_id` index check and an insert-only grant for `app_user`.
- Load test: seed 1,000 companies × 20 products × 200 findings, then check admin pages and company pages for response times and query plans.
- Security pass: rate limits, `?next=` handling, IDOR checks on every route taking an ID, and the CSP still holds.

**Exit checks:** the isolation suite passes as `app_user`. Admin Overview loads in under 500 ms with 1,000 companies. A load-test company page loads in under 300 ms on the server.

---

## P10 · Email go-live (on hold)
- Choose a provider and add its transport file. A cron job sends `pending` rows with retries and backoff, and marks them `sent` or `failed`.
- Set up SPF, DKIM and DMARC for the sending domain.
- Switch `EMAIL_TRANSPORT`. Nothing else changes: every flow already sends through the outbox.

## As built (P2–P9)

**Neon** was migrated to v2 on 2026-11-14. Before the reset it held one Super Admin, 4 sessions and 9 audit rows. That Super Admin was carried over with the same password hash. The app now connects as `vapt_app`, a member of `app_user`, so row-level security is enforced in development and production. Migrations, the seed script and `pnpm user:create` use `MIGRATION_DATABASE_URL`, which connects as the table owner.

**Checks:**
- 42 tests across roles, tenancy, row-level security, domain rules and testing.

**Known gaps**, deliberately left for later:
- A 404 inside the console streams with HTTP 200, because the root `loading.tsx` streams the page first. The content is the not-found page.
- SLA reminder and abandoned-sign-up **emails** aren't built. Both show in-app (notifications, Admin → Sign-ups).
- Single-finding Markdown downloads stay client-side and aren't audited.
- P10 (email provider) is on hold.
